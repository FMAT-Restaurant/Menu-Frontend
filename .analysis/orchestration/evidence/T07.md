## 1. Resumen de Implementación

### 1.1 Comprobación de Pertenencia de Oferta a Entrada (`O11`)
- En `src/features/offers/OfferFormPage.tsx`, dentro del efecto de carga inicial de datos (`getEntry` y `getOffer`), se valida la correspondencia de la oferta:
  ```typescript
  if (offerData && !restoredFromStorageRef.current) {
    if (offerData.data.entryId && offerData.data.entryId !== entryId) {
      setLoadError("La oferta no pertenece a la entrada seleccionada.");
      return;
    }
    // ...
  }
  ```
- Al producirse un error de pertenencia, la condición `!loading && !loadError` impide el renderizado del `<form>` y de cualquier control de edición o guardado.
- Asimismo, se suprime el botón `"Reintentar"` ante este error específico, ya que la ruta es estructuralmente inválida.
- En `handleSaveOffer`, se valida de forma defensiva la correspondencia antes de iniciar cualquier despacho hacia el backend.

### 1.2 Aislamiento Contextual y Limpieza ante Cambio de Ruta (`O12`)
- Se implementó un efecto de reinicio reactivo a los parámetros de ruta `[entryId, offerId]`:
  ```typescript
  useEffect(() => {
    imageValidationId.current += 1;
    controllerRef.current = null;
    confirmedImageIdRef.current = null;
    openingEtagRef.current = undefined;
    sentSlotsRef.current = [];
    restoredFromStorageRef.current = false;
    isSubmittingRef.current = false;

    setPresentationTag("");
    setBasePrice("");
    setDesiredStatus("INACTIVE");
    setSlots([]);
    setSelectedFile(null);
    setPreviewUrl("");
    setExistingImage(null);
    setImageError("");
    setImageValidating(false);
    setFormError("");
    setConflictNotice("");
    setAmbiguousNotice("");
    setAmbiguousResponse(null);
    setUncertainStage(null);
    setRetryCountdownMs(0);
    setReviewedOffer(null);
    setReviewLoading(false);
    setSlotModalOpen(false);
    setEditingSlotIndex(null);
    setOptionModalOpen(false);
    setTargetSlotIndex(null);
    setEditingOptionIndex(null);
    setCurrentOptionDraft(null);
    setRecipePickerOpen(false);
    setSaving(false);
  }, [entryId, offerId]);
  ```
- El incremento `imageValidationId.current += 1` invalida cualquier validación asíncrona de imagen en vuelo proveniente del contexto anterior, previniendo que una resolución demorada altere el nuevo contexto.
- `activeContextRef.current = { entryId, offerId }` previene que callbacks tardíos de mutaciones en vuelo de una ruta previa alteren el estado o naveguen fuera del contexto activo.

### 1.3 Bloqueo de Concurrencia y Validación de Imagen (`O16`)
- Se introdujo `isSubmittingRef = useRef(false)`.
- En `handleSaveOffer`:
  - Se evalúa de inmediato: `if (isSubmittingRef.current || saving) return;`
  - Se evalúa el estado de validación de imagen: `if (imageValidating) { setFormError("La imagen se está validando. Espera a que termine la validación."); return; }`
  - El botón submit `<button type="submit">` se deshabilita condicionalmente ante `saving || imageValidating || isSubmittingRef.current`.
  - Múltiples clics simultáneos comparten la operación en curso sin duplicar llamadas a `repository.createOffer` o `repository.updateOffer`.
- En `handleManualRetry`, se aplica la misma protección secuencial mediante `isSubmittingRef`.

### 1.4 Reutilización de `imageId` Confirmado en Reintentos (`O17`)
- La arquitectura en dos fases provista por `OperationAttemptController` confirma la carga de imagen en la etapa 1 y almacena `confirmedImageId`.
- Si la etapa 2 (`createOffer` o `updateOffer`) falla con incertidumbre o caída de red, `confirmedImageIdRef.current` retiene el identificador confirmado.
- Al pulsar `"Reintentar"`, `controller.retryPending()` reintenta exclusivamente la etapa 2 con el mismo `idempotencyKey`, payload JSON sellado y el `imageId` previamente confirmado, sin volver a invocar `uploadEntryImage` ni rotar la clave.

### 1.5 Invalidación de Entradas del Catálogo y Recorrido E2E (`O18`)
- Se importa `invalidateCatalogEntries(repository)` desde `src/application/catalogCache.ts`.
- Se invoca al confirmar exitosamente una creación o actualización de oferta en `handleSaveOffer`, en `handleManualRetry` y al adoptar una versión de servidor en `handleAdoptReviewedOffer`.
- Se implementó el archivo E2E dedicado `e2e/offer-form.spec.ts` que valida el recorrido completo dentro del TTL de 30 segundos sin recarga (F5):
  1. Catálogo inicial con 0 ofertas (`Ofertas: 0`).
  2. Navegación al listado de ofertas de la entrada.
  3. Navegación al formulario de creación y guardado exitoso con imagen, grupo y opción asignada.
  4. Retorno al catálogo sin F5: se constata `Ofertas: 1`.
  5. Navegación al listado y eliminación de la oferta mediante diálogo modal.
  6. Retorno al catálogo sin F5: se constata `Ofertas: 0`.

### 1.6 Errores Estructurados y Conflictos Contractuales (`O20`, `O33`)
- Se reemplazó el extractor plano por `extractStructuredErrorMessage(err)`, utilizando `contractErrorResponse(data)`:
  - Extrae el mensaje contractual y concatena las descripciones de `details.violations` (`path` y `message`).
  - No reduce las respuestas 422 ni 412 a textos genéricos de Axios (`AxiosError: Request failed with status code 422`).
  - Mantiene intacto el borrador del formulario para permitir su corrección y nuevo envío.

### 1.7 Recarga Efectiva en Modo Edición (`O32`)
- Se actualizó la prueba de reintento en edición para simular un fallo en `getOffer`.
- Verifica que el formulario no renderiza campos durante el estado de error de carga.
- Al pulsar `"Reintentar"`, verifica que se invocan efectivamente tanto `getEntry` como `getOffer` (dos llamadas cada uno).
- Verifica que los datos recuperados (`presentationTag`, `basePrice`, grupos y opciones) se pueblan de manera efectiva en los campos del formulario.
