## 1. Resumen de Implementación

### 1.1 Modelo y Tipos (`src/application/catalog.ts`)
- Se ajustó la interfaz `EntryUpdateDraft`:
  ```typescript
  export interface EntryUpdateDraft extends EntryCreateDraft {
    status?: EntryStatus;
    imageId?: string;
  }
  ```
  Permite omitir el campo `status` en el payload de actualización PATCH cuando no hubo un cambio de estado administrativo.

### 1.2 Transición Contractual en API (`src/api/menuApi.ts`)
- Se retiró la excepción artificial previa en `setEntryStatus`:
  - Se eliminó el bloqueo `if (status === "ACTIVE") throw new Error(...)`.
  - Ahora se permite solicitar la transición contractual `ACTIVE` enviando `PATCH /menu/entries/:id` con `{ status: "ACTIVE" }` y la cabecera `If-Match` del recurso vigente.
  - En caso de rechazo del backend (ej. 422 si no cumple invariantes de ofertas activas), el error HTTP se propaga con su detalle correspondiente.
  - `updateEntry` mantiene el ETag de apertura con cabecera `If-Match` fuerte sin GET intermedio ni cabecera `Idempotency-Key` (reservada para creaciones y PATCH de ofertas).

### 1.3 Clasificación de Errores HTTP 428 (`src/features/entries/entryError.ts`)
- Se incluyó HTTP 428 (`Precondition Required`) en la clasificación de conflictos (`FailureKind = "conflict"`):
  ```typescript
  if (status === 409 || status === 412 || status === 428) return "conflict";
  ```
- Ante 428, el formulario detiene el envío, conserva el borrador editable intacto y ofrece la acción explícita de "Revisar entrada actual".

### 1.4 Lógica del Formulario de Entradas (`src/features/entries/useEntryForm.ts`)
- **Omisión de `status` en edición de texto (`E03`):**
  En `persist()`, se evalúa si `resources.entry?.status !== draft.status`. Si no hubo cambio (ej. editar la descripción de una entrada que ya está `ACTIVE`), `status` se omite del payload PATCH.
- **Protección contra fallos en `onSaved` (`E04`):**
  - Se introdujo la bandera `saveSucceeded` en el hook.
  - Tras confirmarse el éxito remoto (`persist` o `controller.submit()`), se marca `saveSucceeded.current = true` y se invalida la caché de catálogo.
  - La ejecución de `await onSaved()` se encapsula en un bloque `try...catch`. Si el callback de navegación o refresco falla, no se altera el éxito confirmado, no se marca la operación como incierta y cualquier submit posterior es ignorado de inmediato.
- **Identificación de imagen en revisión de conflicto (`E02`):**
  Se proveen los datos para identificar el estado de imagen remoto vs local en `EntryReview`.

### 1.5 Revisión de Conflictos con Visibilidad de Imágenes (`src/features/entries/EntryFormFeedback.tsx`)
- En `EntryReview`, se añadieron secciones explícitas en el `<dl>` para contrastar:
  - **Imagen actual en servidor:** Muestra `<img>` y su URL si existe, o referencia de imagen, o el texto `"Sin imagen"` si está ausente.
  - **Imagen en borrador local:** Muestra `"Archivo local: <nombre>"` si hay un archivo seleccionado, la imagen/referencia previa conservada, o `"Sin imagen"`.
- Permite al usuario identificar visualmente y textualmente el cambio concurrente de imagen antes de elegir si adoptar los datos remotos o continuar con su borrador.

### 1.6 Interfaz y Deshabilitación de Guardado (`src/features/entries/EntryFormPage.tsx`)
- Se expuso la propiedad `onSaved?: () => Promise<void>` en `EntryFormPageProps` y `EntryFormEditor` para desacoplar y permitir inyección de callbacks en pruebas.
- Se agregó `model.saveSucceeded` a la condición de `saveDisabled`, garantizando que una vez persistida la entrada, el botón permanezca deshabilitado evitando reenvíos accidentales.

## 2. Fortalecimiento y Aislamiento de Pruebas

### 2.1 Inspección Exacta de Cuerpos (`src/api/entryApi.remediation.test.ts` — `A06`)
- En las pruebas de creación (`POST /menu/entries`) y edición (`PATCH /menu/entries/:id`), se inspeccionó el payload exacto para validar la presencia de `imageId: "uploaded-1"`.
- Se agregó un test específico que verifica que omitir o alterar `imageId` provoca el fallo estricto de la aserción.

### 2.2 Nombres Contractuales y Rechazo Integrado de Imagen (`src/api/menuApi.contract.test.ts` — `A07`)
- Se renombraron las pruebas unitarias a `rejects image upload when the upload request fails` y `rejects image upload when the upload response has no imageId`.
- En `EntryFormPage.test.tsx`, se implementó una prueba integrada donde el usuario interactúa con el formulario completo (imagen y campos) y la subida de imagen es rechazada (HTTP 422): se constató que la UI muestra la alerta y que `api.createEntry` nunca llega a ser invocado (0 llamadas).

### 2.3 Aislamiento de Globals y Limpieza Garantizada (`src/features/entries/EntryFormPage.test.tsx` — `E06`, `E08`)
- Se implementó captura de descriptores originales y ganchos de configuración y restauración:
  - `beforeEach`: Prepara descriptores frescos e independientes para `URL.createObjectURL` y `URL.revokeObjectURL`.
  - `afterEach`: Restaura mediante `restoreGlobal` los descriptores de `createImageBitmap`, `createObjectURL`, `revokeObjectURL`, `requestAnimationFrame`, `scrollBy` y `scrollTo`, ejecutando además `jest.restoreAllMocks()`.
  - Garantiza que cualquier excepción o fallo en una aserción no contamine las pruebas subsecuentes.

### 2.4 Cancelación con Modificación Real (`src/features/entries/EntryFormPage.test.tsx` — `E07`)
- Se implementó la prueba donde se modifican nombre, descripción y se selecciona una imagen válida antes de pulsar "Cancelar".
- Se comprobó el retorno a la URL con filtros preservados y, al reabrir el formulario, se constató el borrador inicial limpio (campos vacíos, sin imagen previa) y 0 persistencias en el repositorio.

### 2.5 Pruebas E2E (`e2e/entry-form.spec.ts` y `e2e/entry-form-remediation.spec.ts`)
- Se ajustó `e2e/entry-form.spec.ts` para validar que cuando una entrada es editada sin cambiar su estado, el cuerpo del PATCH omite la propiedad `status`.
